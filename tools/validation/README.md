# Проверка инструментов Лаймо

Эти скрипты проверяют доступность диагностики, а не доказывают попиксельное совпадение с системным iOS. Перед запуском читать корневой AGENTS.md. Они не управляют физическим iPhone.

## Среда

Mac с Xcode, запущенным симулятором, Python 3 и FFmpeg/ffprobe. В simulator_smoke.py FFmpeg вызывается из Homebrew /opt/homebrew/bin. Сторонние Python-пакеты не нужны. Для Safari MCP нужен Safari с поддержкой `safaridriver --mcp` (проверено на Safari 27.0).

Из ограниченного sandbox системные службы могут быть недоступны. Использовать разрешённый доступ к системным инструментам; не менять настройки устройства автоматически.

## Safari iOS в симуляторе

Узнать UDID только нужного запущенного симулятора:

```sh
xcrun simctl list devices booted
```

Создать временную папку для результатов и выполнить из checkout проекта:

```sh
python3 tools/validation/simulator_smoke.py --root . --out /private/tmp/laimo-validation --simulator-udid <UDID_СИМУЛЯТОРА>
```

Скрипт:
- отдаёт index.html с диагностикой, добавленной только в HTTP-ответ в памяти; исходники не переписывает;
- собирает JS-исключения, unhandled rejection, ошибки ресурсов и console.warn/error с начала загрузки;
- записывает специальный console.warn `__probe_sentinel__`, чтобы проверить сам сборщик; это ожидаемое сообщение;
- открывает страницу через simctl, проверяет ITB/GLS, меняет вкладки API ITB.set по последовательности 1→2→3→0 и сверяет DOM/ARIA;
- снимает PNG и H.264-видео, читает реальные временные метки кадров, извлекает PNG-кадр;
- сохраняет JSON и журнал HTTP, останавливает собственные сервер и запись.

Артефакты — только в указанной --out папке; там могут быть большие видео/PNG. По завершении удалить собственную временную папку. Если Safari симулятора запускался для этого теста, завершить его после работы:

```sh
xcrun simctl terminate <UDID_СИМУЛЯТОРА> com.apple.mobilesafari
```

Запись симулятора имеет переменные интервалы. Поле r_frame_rate может быть 600/1 при гораздо меньшем фактическом avg_frame_rate. Нельзя считать это частотой дисплея или мерой плавности приложения. Использовать временные метки; длинные паузы записи статического кадра не приравнивать автоматически к зависанию UI.

Тестовый сценарий не покрывает ручной drag/hold, все особенности панели Safari, fallback старых устройств и физическую плавность. Фиксированная ссылка ?v=123 в HTTP-запросе — кэш-параметр диагностического запуска; реальную версию брать из footer/кода и обновлять сценарий по мере изменений.

## Safari MCP на Mac

```sh
python3 tools/validation/safari_mcp_smoke.py --out /private/tmp/laimo-validation
```

Запускает `safaridriver --mcp` как отдельный stdio-процесс, выполняет initialize, открывает только собственную вкладку опубликованного Лаймо, читает состояние страницы/GLS, консоль и сводку неуспешных запросов, затем закрывает свою вкладку и процесс. Не читает чужие вкладки и не управляет телефоном. URL сейчас v123; при изменении версии обновить его.

Все действия с tab handle должны выполняться в одном MCP-процессе: после нового запуска старый handle может быть недействителен. Пустой список network requests не подтверждает отсутствие ошибок: буфер может не содержать ранние запросы. Сопоставлять с консолью, локальным журналом HTTP и адресными проверками ресурсов.

Скрипт сохраняет ответы инструментов; наличие error в консоли требует разбора и не превращается автоматически в «всё чисто».

## Физический iPhone: только разрешённые действия

После явного разрешения пользователя и проверки, что впереди разрешённый экран:
- открытие конкретного приложения — devicectl device process launch;
- открытие только страницы Лаймо — тот же launch с --payload-url и com.apple.mobilesafari;
- PNG — devicectl device capture screenshot --device <id> --destination <временный.png>.

Не использовать автоматические касания, не открывать настройки/другие приложения/личные данные, не переустанавливать без отдельного разрешения. Полный PNG временно нужен для точного исходного размера; для анализа выбирать участок меню, затем удалять ненужный полный кадр. Личные данные не загружать в публичный GitHub.

На проверенном iPhone 17 Pro команда devicectl screen-record возвращает Unsupported Capability. Наличие команды в --help не означает поддержку телефоном. Отдельный физический видеозахват ещё не настроен. До его проверки не заявлять, что запись с телефона работает.

## Проверенный результат 08.11.2026

- Физический iPhone: успешно открыты Glass, Fitness, Health, Safari/Лаймо. PNG Glass/Fitness/Safari — 1206×2622. Health только открыт, без анализа медицинских данных.
- Восстановленный Glass запускается после ручного доверия пользователем.
- По сообщению пользователя системное стекло сейчас более прозрачное, а сайт воспроизводит тонированный режим. Это ожидаемая разница настроек, не дефект; настройки не менялись.
- Симулятор: четырёхэкранный сценарий прошёл; GLS.on=true, GLS.err пусто, JS-исключений и ошибок ресурсов сценария нет; sentinel принят.
- Переносимый прогон: 477 кадров, 10.320 с, 1206×2622; временные метки монотонны. Извлечение кадров и попиксельное сравнение проверены.
- Опубликованная страница и menu.js — HTTP 200; favicon.ico — HTTP 404, также виден в консоли Safari. Значок не исправлялся в рамках настройки инструментов.
- WebDriver-сессия симулятора не создалась («no matching session hosts»). Рабочий обход: simctl + локальная диагностика страницы; отдельная MCP-сессия Safari на Mac.
- Совпадение стекла/анимаций с эталоном в этой задаче НЕ оценивалось.
